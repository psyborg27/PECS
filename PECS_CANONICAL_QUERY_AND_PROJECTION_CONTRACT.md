# PECS Canonical Query and Projection Contract

## Purpose

This document defines the single canonical PECS query contract and the corresponding projection contract for all supported consumers.
It is consumer-agnostic: the contract is independent of Copilot, Continue, Kimi, and CommandCode.
The contract is compatible with the current PECS-PRO and PECS-LITE architecture and does not redesign the architecture.

## Part 1 — Canonical Query Contract

### Contract shape

A canonical PECS query is a single JSON envelope that contains:
- consumer metadata
- model metadata
- profile and projection directives
- workspace context
- task framing
- locality and authority expectations
- execution semantics
- constraints

The query is intentionally abstracted away from consumer-specific payloads.

### Canonical query fields

#### Mandatory fields

- `query_id`: string
  - unique per query request
- `consumer`: string
  - canonical consumer identifier such as `copilot`, `continue`, `kimi`, `commandcode`, or `other`
- `workspace_id`: string
  - canonical workspace identifier or path hash
- `projection_profile`: object
  - the profile instructions for PECS-LITE
- `task_type`: string
  - `bug_fix`, `feature_addition`, `refactor`, `inspection`, `validation`, `documentation`, or `other`
- `issue`: string
  - the primary issue, feature request, or task description
- `execution_mode`: string
  - `development`, `inspection`, `repair`, `test`, `review`, or `analysis`
- `constraints`: object
  - hard constraints such as max targets, token budget, or exploration budget
- `timestamp`: string
  - ISO8601 timestamp of the query

#### Required profile fields

Within `projection_profile`, the following are mandatory:
- `profile`: string
  - `large`, `medium`, `small`, or `execution`
- `reasoning_budget`: string
  - `low`, `medium`, `high`, or `very_high`
- `exploration_constraints`: string
  - `strict`, `bounded`, or `expanded`
- `target_count`: integer
  - suggested maximum number of projected candidates
- `continuity_depth`: string
  - `minimal`, `balanced`, or `deep`
- `include_advisories`: boolean
  - whether to include advisory commentary in the response

#### Optional fields

- `engineering_intent`: string
  - e.g. `maintainability`, `performance`, `security`, `UX`, `compatibility`
- `feature`: string
  - alternate natural-language task label or feature summary
- `requested_authority`: string
  - `strict`, `balanced`, or `exploratory`
- `requested_locality`: string
  - `file`, `class`, `function`, `module`, `package`, or `system`
- `requested_fields`: string[]
  - consumer requested corpus such as `runtime_targets`, `authority_breakdown`, `consulted_artifacts`
- `metadata`: object
  - consumer-specific metadata, such as `user_intent`, `reasoning_capability_class`, or `caller_context`

#### Derived automatically

These fields should be generated by the consumer adapter or the PECS runtime as needed:
- `model` / `model_name`: string
  - normalized consumer model identifier, derived from provider metadata when missing
- `requested_authority`: if omitted, derived from `projection_profile.profile`
- `requested_locality`: if omitted, derived from `task_type` and `issue`
- `workspace`: string
  - if `workspace_id` is a hash, a normalized workspace path may be derived from local context
- `query_source`: string
  - normalized from consumer-specific source and appended to observability metadata
- `profile_class`: string
  - derived classification such as `small`, `medium`, `frontier`, or `execution`

## Part 2 — Projection Profiles

The projection profile determines how much evidence is returned and how much locality is exposed.
Each profile is a view onto the same underlying PECS authority/continuity architecture.

### Large profile

Large models receive the fullest evidence-rich projection.
The contract for `large` should return:
- top 3 candidate object groups (or top 3 candidate localities when object groups are not yet implemented)
- `authority_breakdown`
- `authority_inputs`
- `locality_confidence`
- `authority_confidence`
- `object_evidence_summary`
- `consulted_artifacts`
- `influential_artifacts`
- `current_file`
- `current_class`
- `current_function`
- `current_code_block_range`
- `modularization_guidance`
- `observability_information`

Large profile is evidence-heavy and transparent. It is designed for deep reasoning models that can consume detailed authority and locality context.

### Medium profile

Medium models receive a balanced projection.
The contract should return:
- top 2–4 candidate object groups or localities
- authority breakdown summary
- locality confidence
- authority confidence
- consulted artifacts
- influential artifacts
- current file/class/function
- current code block range
- brief advisory notes

Medium profile is the default for most capable local models and moderate-capacity remote models.

### Small profile

Small models receive the minimal high-value projection.
The contract should return:
- highest authority candidate only
- `current_file`
- `current_class`
- `current_function`
- `current_code_block_range`
- `locality_confidence`
- `authority_confidence`
- brief warning when authority is weak

Small profile should avoid low-value evidence and should not return detailed evidence breakdowns beyond what is necessary for safe narrowing.
It should favor highest-confidence locality and leave broader exploration to consumer follow-up.

### Execution profile

Execution-oriented models receive deterministic execution guidance.
The contract should return only execution-critical information:
- selected execution candidate locality
- `current_file`
- `current_function`
- `current_code_block_range`
- `locality_confidence`
- `authority_confidence`
- explicit `execution_targets`
- `implementation_guidance` limited to deterministic scope
- `observe_only` or `execute_only` advisory flags

Execution profile is optimized for models built to perform code transformations or runtime implementations with minimal ambiguity.

### Profile return summary

| Profile | Returns | Purpose |
|---|---|---|
| `large` | evidence-rich authority and locality report | exploratory, deep reasoning |
| `medium` | balanced locality and authority summary | broad but constrained reasoning |
| `small` | minimal highest-authority candidate | narrow context, low token usage |
| `execution` | deterministic execution locality | implementation-focused |

## Part 3 — Progressive Disclosure

PECS should support progressive projection as an optional contract pattern.

### Recommended approach

- The canonical contract may allow an initial minimal response and a subsequent expansion request.
- This should be expressed through query fields such as:
  - `requested_fields`
  - `progressive_disclosure`: object
  - `expand_after`: `string`
- A second query may request additional evidence or candidates.

### Architectural position

Progressive disclosure is a supported extension, not a required core behavior.
It fits the current architecture because PECS-PRO and PECS-LITE already separate authority generation from projection selection.
The architecture can support:
- initial response with focused locality
- follow-up request for additional evidence
- expanded candidate list
- complete authority report when requested

### Recommendation

Yes, progressive projection should be part of the contract as an optional capability.
It should not be mandatory for all consumers, but it should be explicitly supported by the query contract.

## Part 4 — Consumer Interpretation Guidance

### Large models

- Authority is probabilistic; treat scores as evidence indicators, not absolute truth.
- Locality is the most stable guidance.
- Read the code before acting.
- Use authority and locality together to prioritize candidates.
- Do not assume a high score means the code is the only valid edit point.

### Small models

- Begin with the highest-authority candidate.
- Read only the returned code block.
- If the candidate is unsuitable, discard the current active context for that candidate and move to the next.
- Only perform a broader search if all returned candidates fail.
- Prefer minimal exploration and avoid using the small model as a full workspace search engine.

### Execution models

- Treat returned locality as deterministic execution-critical information.
- Implement the code within the returned file/function/block.
- Do not perform broad semantic search beyond the explicit candidate locality.
- Use the projection as the primary execution target; verify authority confidence before broadening.

## Part 5 — Canonical Response Contract

The response contract is a canonical wrapper with a fixed field ordering.

### Canonical response structure

1. `schema`
2. `query_id`
3. `workspace_id`
4. `status`
5. `PECS_Status`
6. `PECS_Query`
7. `PECS_Response`
8. `PECS_Confidence`
9. `Relying_On_PECS`
10. `Reason`

### Canonical response content

#### `PECS_Status`
- `queried_pegs`: boolean
- `runtime_mode`: string
- `projection_mode`: string
- `runtime_observability_used`: boolean
- `engineering_continuity_used`: boolean
- `consulted_artifacts`: string[]
- `missing_artifacts`: string[]
- `artifact_writes`: integer
- `validation_state`: string
- `fallback_reason`: string
- `reason`: string

#### `PECS_Query`
- exactly echo query fields and profile

#### `PECS_Response`
- `runtime_targets`: object[]
- `secondary_neighbors`: object[] or string[]
- `authority_breakdown`: object[]
- `authority_inputs`: object
- `consulted_artifacts`: string[]
- `influential_artifacts`: string[]
- `current_locality`: {
  - `file`: string
  - `class`: string
  - `function`: string
  - `code_block_range`: object
}
- `locality_confidence`: number
- `authority_confidence`: number
- `final_locality_selected`: object
- `final_authority_selected`: object
- `modularization_guidance`: object|null
- `observability`: object

#### `PECS_Confidence`
- `authority_confidence`: number
- `authority_confidence_band`: string
- `tier_contributions`: object
- `evidence_balance`: object

#### `Relying_On_PECS`
- `pegs_used`: boolean
- `pegs_observed`: boolean
- `pegs_influence`: string
- `fallback_reason`: string

### Response order within `PECS_Response`
1. `runtime_targets`
2. `secondary_neighbors`
3. `authority_breakdown`
4. `authority_inputs`
5. `consulted_artifacts`
6. `influential_artifacts`
7. `current_locality`
8. `locality_confidence`
9. `authority_confidence`
10. `final_locality_selected`
11. `final_authority_selected`
12. `modularization_guidance`
13. `observability`

### Candidate object group representation

For current consumers, object groups may be represented as candidate localities with a primary object grouping label.
When object group support is available, add:
- `candidate_object_groups`: object[]
- `group_authority_score`: number
- `group_evidence_summary`: object

## Most Important Question

### Can one canonical query contract support all current and future PECS consumers by varying only the projection profile?

**Answer: YES**

### Justification
- The contract is consumer-independent: `consumer` is metadata, not a structural dependency.
- The same fields and wrapper can support Copilot, Continue, Kimi, and future consumer types.
- Different projection profiles only change the depth and breadth of evidence returned, not the contract shape.
- This matches the current PECS architecture: PECS-PRO supplies evidence and authority, while PECS-LITE adjusts projection breadth by profile.
- As long as consumers preserve the canonical response order and interpretation guidance, one contract suffices.
