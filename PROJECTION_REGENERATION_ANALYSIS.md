# PROJECTION_REGENERATION_ANALYSIS

## What regenerates projections

### `topology_compact.json`

Regenerated by:
- `WorkspaceContinuityDaemon._rebuild_runtime_topology()`

This occurs when:
- the daemon detects `.py` file changes
- startup requires a full scan because artifacts are missing or invalid

Not regenerated by:
- chat history updates
- runtime activation updates
- bridge refresh itself

### `compact_bundle.json`

Regenerated by:
- `_rebuild_runtime_topology()`
- `_on_chat_history_update_unlocked()`
- `_on_activation_update()`

This means the compact projection is intended to stay in sync with:
- workspace topology
- user chat focus signals
- runtime activation events

### `active_context.json`

Regenerated by the same paths as `compact_bundle.json`.

### `ai_chat_history.json`

Regenerated only by external append operations and daemon system events.
The daemon does not synthesize chat history from workspace activity.

## Where regeneration is skipped

### Bridge export is not a regenerate step

`.pecs/bridge/export_workspace_continuity.py` does not rebuild core runtime artifacts.
It only reads existing:
- `topology_compact.json`
- `locality_index.json`
- `compact_bundle.json`
- `active_context.json`
- `session_context.json`
- `daemon_state.json`

and writes continuity export artifacts. Therefore a successful bridge refresh can still leave stale core runtime projections.

### Throttling and stale refresh state

`WorkspaceContinuityDaemon._run_continuity_refresh()` uses `_should_run_continuity_refresh()` with a 60-second throttle.
If multiple triggers occur within 60 seconds, later triggers are skipped.
That may delay freshness, but it does not explain a persistent stale state if the first trigger produced fresh core artifacts.

### Runtime locality condition

`_on_chat_history_update_unlocked()` only rebuilds compact/context if `self.runtime_locality_payload` is present.
If the daemon has not yet built runtime locality, chat updates will still refresh authority state but will not regenerate `compact_bundle.json` or `active_context.json`.

## What the current implementation can miss

1. `ai_chat_history.json` can remain stale if the external `.pecs/tools/append_ai_chat_history.py` path is not used by incoming Copilot/Continue events.
2. `topology_compact.json` can remain stale if no `.py` changes are detected by the daemon, even when the workspace runtime changes.
3. `compact_bundle.json` / `active_context.json` can remain stale if chat updates occur without valid workspace runtime locality or if the computed focus is generic.
4. The bridge refresh step does not validate or trigger rebuild of stale core runtime artifacts.

## Core propagation boundary

The effective boundary is:

workspace activity → daemon extraction/rebuild → core `.pecs` artifacts → bridge export

The last step is healthy, but the preceding step is currently the only place where stale artifacts can persist.

## Practical verification points

To verify automatic refresh propagation, each of these must be confirmed independently:
- `ai_chat_history.json` is appended by Copilot/Continue to `.pecs/ai_chat_history.json`
- `.py` file changes are seen by `WorkspaceContinuityDaemon._record_change()` and trigger `_rebuild_runtime_topology()`
- runtime activation events are written to `.pecs/runtime_activation.jsonl` and trigger `_on_activation_update()`
- each rebuild path writes `compact_bundle.json`, `active_context.json`, and `topology_compact.json` as appropriate
- `_execute_bridge_refresh()` reads those artifacts and exports continuity state
