# PECS INSTALLER AUDIT

## Overview

This audit inspects the PECS installer and workspace asset management mechanisms in `/Users/raj/Developer/PECS` to confirm preservation behavior, upgrade semantics, and bridge integration.

## Primary Installer Components

### `install_workspace_integration.py`

- Responsible for workspace bootstrap, asset installation, and legacy compatibility
- Handles `.continue`/`.github` asset creation and `.pecs` workspace integration
- Uses backup-aware file writes to preserve user content and existing workspace configuration

### `workspace_assets_manager.py`

- Manages manifest-based workspace assets
- Reads `workspace_assets_manifest.json` to determine preserve/merge rules
- Supports `copy_canonical_asset`, `write_managed_text_asset`, and `merge_json_dict`
- Provides robust upgrade semantics for `.vscode` and `.continue` assets

### `workspace_bridge_cli.py`

- Exposes CLI commands for install, bootstrap, refresh, rebind, and status
- Uses the same workspace root and artifact directories as the daemon
- Provides `install-workspace-assets`, `bootstrap-workspace`, and `refresh-workspace`

## Preservation Behavior

### Continuity artifact preservation

- `.pecs/ai_chat_history.json` is explicitly preserved by the installer and not overwritten during asset installation.
- `.pecs/continuity/*.json` and `.pecs/continuity/*.md` are generated by the continuity bridge and should remain user-managed/generated artifacts.
- Existing continuity exports are preserved unless the bridge refresh path regenerates them.

### Backup semantics

- Installer takes backups of modified workspace assets before writing.
- Backup files are typically named with `.bak` or specific backup directory paths.
- This ensures rollback capability for `.continue/config.yaml`, `.github/copilot-instructions.md`, and `.vscode` settings.

### Merge semantics

- `.vscode/tasks.json` and `.vscode/settings.json` are merged using JSON dict merge helpers
- Existing `copilot-instructions.md` is appended or merged rather than overwritten
- `.continue` rules are written with existing content preservation in mind

## Installer and Bridge Interaction

### `install_workspace_integration.py` flow

- Bootstraps workspace-level `.continue` and `.github` assets
- Installs `.pecs` support files and bridge scripts
- Writes the bridge runtime into `.pecs/bridge`
- Does not directly trigger continuity export on install
- Relies on the daemon or explicit `refresh-workspace` command for bridge execution

### `workspace_bridge_cli.py` flow

- `bootstrap-workspace` installs assets and may initialize the `.pecs` daemon environment
- `refresh-workspace` explicitly runs the bridge refresh path
- `rebind-workspace` can reinitialize workspace asset references without changing continuity state

## Bridge Refresh Implementation

### Daemon-triggered bridge refresh

- `workspace_continuity_daemon.py` calls `_execute_bridge_refresh()` when runtime activation or chat history changes
- `_execute_bridge_refresh()` prefers `run_bridge.sh` if executable, else `run_bridge.py`
- It runs `refresh` with the current workspace root and captures stdout/stderr
- Refresh status is stored in `.pecs/continuity_refresh_state.json`

### Bridge CLI refresh

- `.pecs/bridge/run_bridge.py refresh --workspace <workspace>` executes the export path
- This command is the same one used by the daemon and by manual user invocation
- A failure during refresh logs the command and raises a `RuntimeError`

## Risks and Gaps

### No Kimi-specific assets or logic

- Current installer manifest does not include Kimi integration assets
- There is no `kimi/` directory or Kimi-specific configuration in the workspace

### Refresh-on-install is not automatic

- The installer writes workspace assets but does not guarantee an immediate continuity export
- Continuity exports remain stale until the daemon triggers a refresh or a user runs `refresh-workspace`

### Preservation vs regeneration

- The installer preserves generated continuity artifacts, but the bridge itself can overwrite exports during refresh
- There is no explicit versioned backup of `.pecs/continuity/*` on refresh

## Recommendations for Kimi Integration

- Add Kimi assets to `workspace_assets_manifest.json` with preserve rules
- Ensure the install path does not overwrite `.pecs/ai_chat_history.json`
- Support installation of Kimi workspace rules under `.kimi/` or equivalent
- Document that bridge refresh is a separate step from install

## Conclusion

The PECS installer is preservation-first and uses manifest-driven workspace asset management. Continuity artifacts are protected during install, but the bridge refresh process remains the authoritative path for regenerating `.pecs/continuity/*`. Kimi integration should follow the same asset model and preserve existing continuity state during upgrade.
