# PECS KIMI CONTINUITY INGESTION

## Purpose

This document defines how Kimi should ingest and generate continuity events within a PECS-integrated workspace.

## Existing Continuity Ingestion Model

### Canonical ingestion sink

- `.pecs/ai_chat_history.json` is the single source of truth for chat-history-based continuity events.
- `append_ai_chat_history.py` is the ingestion utility used by Continue and Copilot to add normalized events.
- The daemon watches `.pecs/ai_chat_history.json` and triggers bridge-based continuity refreshes.

### Normalization goals

Each event is normalized to include:

- `workspace_root`
- `workspace_id`
- `source`
- `event_type`
- `message`
- `component`
- `object_ids`
- `correlation`
- `ts`

### Deduplication

- Events are deduplicated by deterministic `event_id` generation.
- Duplicate appends are ignored when the same event payload is present.

## Kimi Ingestion Requirements

### Use the existing pipeline

Kimi continuity ingestion must reuse the existing `.pecs/tools/append_ai_chat_history.py` pipeline.

- Do not introduce a separate event store
- Do not bypass `.pecs` artifact generation
- Use the same event normalization and timestamp semantics

### Kimi-specific event types

Define Kimi event types that capture observable user workflows and continuity state:

- `kimi_query_requested` — Kimi requested a continuity-aware retrieval
- `kimi_query_completed` — Kimi completed a retrieval and made a decision
- `kimi_continuity_suggestion` — Kimi suggested a continuity action or edit
- `kimi_decision_applied` — Kimi applied a continuity-driven change

### Event payload shape

Common required fields:

- `workspace_root`: path to workspace root
- `workspace_id`: canonical workspace identifier
- `source`: `kimi`
- `event_type`: one of the Kimi-specific event types
- `message`: human-readable description
- `component`: Kimi subsystem or module name
- `object_ids`: related object or artifact IDs
- `correlation`: structured correlation metadata
- `ts`: event timestamp
- `metadata`: optional free-form details

## Event append workflow

1. Kimi generates an event in response to user or system action.
2. Kimi normalizes the payload to PECS chat history schema.
3. Kimi writes the event using `.pecs/tools/append_ai_chat_history.py`.
4. The daemon notices the update and calls `_on_chat_history_update_unlocked()`.
5. The daemon triggers `_run_continuity_refresh(trigger="chat_history_update", reason="Kimi continuity event")`.
6. The bridge refresh regenerates `.pecs/continuity/*` artifacts.

## Continuity refresh semantics

### Bridge refresh path

- Kimi ingestion updates `.pecs/ai_chat_history.json`
- Daemon refresh is throttled by `continuity_refresh_throttle_seconds` (default 60s)
- `_execute_bridge_refresh()` runs `.pecs/bridge/run_bridge.sh refresh` or `run_bridge.py refresh`
- Successful refresh updates `continuity_refresh_state.json`

### Failure handling

- If bridge refresh fails, the daemon logs `bridge_execution_failed`
- The failure payload includes command, stdout/stderr, and return code
- The daemon retains previous continuity exports until the next successful refresh

## Installer and upgrade preservation

### Preserve continuity artifacts

- Installation must never overwrite existing `.pecs/ai_chat_history.json`
- Existing `.pecs/continuity/*.md` and `.pecs/continuity/*.json` should be preserved unless explicitly regenerated by the bridge
- Backups must be taken before modifying workspace assets

### Manifest updates

Add Kimi-specific assets to `workspace_assets_manifest.json` with preserve and merge semantics:

- `.kimi/config.yaml`
- `.kimi/rules/PECS_CONTEXT_RULE.md`
- `.kimi/rules/PECS_APPEND_RULE.md`
- `.kimi/instructions.md`

### Integrate with existing installer flows

- `install_workspace_integration.py` should support a `--kimi` or `--all` install target
- `workspace_bridge_cli.py` should expose a Kimi bootstrap/install command if Kimi is enabled
- Kimi assets should be installed using the same backup/append behavior as Continue/Copilot

## Operational guidance

### Kimi app authors

- Emit only normalized PECS continuity events into `.pecs/ai_chat_history.json`
- Prefer `source = "kimi"` and clear `event_type` values
- Avoid large binary payloads in chat history
- Keep text fields concise and actionable

### Debugging

- Use `continuity_refresh_state.json` for refresh status
- Inspect `.pecs/bridge/export_workspace_continuity.py` for the actual export logic
- Use the daemon logs for telemetry events such as `continuity_refresh_started` and `bridge_execution_succeeded`

## Conclusion

Kimi continuity ingestion should be fully aligned with existing PECS chat history and bridge refresh semantics. The integration must not add new continuity stores and must preserve continuity artifacts during install and upgrade.
